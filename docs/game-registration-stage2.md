# 第2段階：ゲーム登録とRules共通化の導入基盤（未有効）

第1段階の画面承認とは分離したドラフト。既存サイト・Firebase・本番のゲーム公開状態には反映しない。

## 実装した基盤

`config/game-registration.json` が18ゲームの教科・単元・正式称号・条件・ポイント・公開チャンネル・最新ゲームの登録元。
`tools/game-registration.mjs` はこの1ファイルから、一覧／管理室用ID、称号カタログ、ポイント設定、保存キー、最高称号、NEW対象、サーバー登録用のマニフェストを生成する。出力先は `.release/` のみ。Firebaseへの送信や本番ファイルの書換えを行わない。

`production-game-registration-candidate.rules` は最後に承認された `production-shikakke-visibility-candidate.rules` を基にした未公開候補。既存の児童プロフィール・ポイント・ランキングの権限は変更していない。新ゲームの個別公開設定は、管理者が監査・バックアップ付きで登録した `productionAdmin/v1/gameRegistry/{gameId}` が有効な場合だけ追加できる。クライアントJSの登録情報だけでは権限を得られない。

`tools/game-registration-store.mjs` は既存の管理者ログインを使い、監査・バックアップ確保→競合再確認→対象文書更新を行うアダプター。画面からの呼出しと本番での実行は未接続。登録してもゲームを自動公開しない。公開状態は別の個別操作で指定する。

## 残す安全条件

- Rulesを反映する前には、読み取り専用接続で本番の現行Rulesとこの候補の基準版を自動照合する。現在値を取得せずに上書きしない。
- 本番・確認用とも、このPRからRulesを公開しない。保留中のRules自動公開開発は再開しない。
- 新しいゲームを確認用だけに登録しても、本番のNEW対象を変えない。公開済みの最新IDは登録元に1つだけ保存する。
- 既存ゲームの公開設定を初期化しない。登録マニフェストと公開状態の設定を分け、既存値を読み取って表示する。
- プロフィールをゲームごとに作り直さない。既存の保存キー、称号ID、最高記録、経済処理の正本を引き継ぐ。
- 既存の一括キャンペーン・一括公開の範囲は自動拡大しない。新ゲームは個別公開操作から接続する。

## 次の統合作業

1. 第1段階の画面を承認後、生成した登録情報を既存ビルダー・教科/単元一覧・管理室・NEWに接続する。
2. 管理室にマニフェストの差分確認と個別登録操作を組み込み、確認用環境で公開/非公開・直接URL制限を検証する。
3. 現行Rulesの再取得、差分、Emulator、確認用の結果をまとめて提示する。
4. 本番Rules変更の承認後に共通化候補を反映する。以後は登録情報と管理室の登録操作だけで、新ゲームごとのRules追加を不要にする。

このドラフトの作成をもって、第2段階の有効化完了とは扱わない。
