# 第2段階の確認用ビルド

登録元は `config/game-registration.json`。既存18ゲームの称号ID、条件、素材、得点ポリシー、記録フィールドと旧保存キーを管理する。通常の確認用と本番ルートは既存の構成で動く。

## 新ゲームを追加する

1. 確認用のゲームページと素材を `stage2/site` の `games/` と `assets/` に配置する。ゲームページは既存の公開判定、ポイント、120秒チャレンジのスクリプトを読み込む。
2. `stage2/site/registrations/<ID>.js` に、そのゲームの問題形式と正誤を検証する `{canonicalPrompt, correct}` を返すコードを追加する。ポイントの付与には既存の経済処理を使う。
3. 登録元に固有ID、教科・単元、入口、記録フィールド、称号と素材を追加し、まず `release.preview` を有効にする。算数は `calculation` または `geometry` を使う。
4. PRの `Game registration preview` が検証用ビルドを生成し、ブラウザーとEmulatorを実行する。成果物の親フォルダーを静的サーバーで提供し、`/preview/index.html` を開く。既存の確認用サイトとは別の参照用ビルドである。
5. 登録用Rulesを導入した確認用Firebaseで、管理室の「新ゲームの個別公開」から登録し、「公開準備中」を経て「公開中」に変更する。

登録と公開状態は別の文書に保存する。登録するだけではプレイできず、公開判定が取れない場合もゲームは開始できない。管理者の個別変更はサーバー側で権限を確認し、変更前後のデータと監査記録を同じトランザクションで保存する。新ゲームの追加は既存の一括公開やキャンペーンの対象を拡大しない。

## 本番導入までに必要な作業

- 確認用Firebaseの現行Rulesを取得し、候補との差分を照合して承認後に適用する。管理者の実セッションで登録、公開、非公開、直接URLを検証する。
- 本番の現行Rulesを取得して候補の基準版と照合し、既存の児童プロフィール・認証・管理権限を含む差分をレビューする。
- 承認後、本番ルートを生成する工程と管理室の登録操作を有効にし、確認したコミットの配信を承認付きのActionsに接続する。登録用Rulesの初回反映と本番配信はこのPRで実行しない。

候補Rulesは `firebase/preview-game-registration-candidate.rules` と `firebase/production-game-registration-candidate.rules`。確認用候補では、元ファイルで閉じ括弧が不足していた称号の条件式をコンパイルできる形に補正した。両候補ともEmulatorで検証する。

## 2026-11-20 実環境との読み取り照合

- 確認用の現行Rulesは `three-game-preview-candidate.rules` の末尾改行を除いた内容と一致。適用中のRulesを基準に登録用の許可を追記した。
- 本番の現行Rulesは `production-shikakke-visibility-candidate.rules` と末尾改行のみの差。候補は新規ゲームの個別登録・公開設定・監査の権限に限定する。
- 既存18ゲームのIDは新規登録から除外し、既存の公開設定に対する別経路を作らない。
- 確認用Rulesの適用と実際の管理室での操作は、Firebase Consoleのセッションと確認用管理者の認証が必要。本番の適用は別途承認する。
