## 今回承認を求める第1段階（閲覧専用）

この段階は管理室全機能の完成ではない。安全な管理者認証と本番データの読み取りを先に確立する。

1. Authenticationでメール/パスワードだけを有効化。メールリンク方式はOFFのまま。Google・匿名は変更しない。
2. 専用アカウント `admin-production@manabi-game-land.invalid` を1件作成。Google用とは別の管理室専用パスワードを利用者自身が安全な入力・本人操作で設定し、チャットやコードに渡さない。既存Googleアカウントや児童Authアカウントは変更しない。
3. 新しいアカウントの実際のUIDを確認後、以下の新規2ドキュメントだけをConsoleで初期設定する。
   - `productionAdmin/v1/private/admin`: uid=実際の専用UID、enabled=true、renameEnabled=false。
   - `productionAdmin/v1/private/revocation`: after=2000-01-01T00:00:00ZのFirestore Timestamp、actor=同じ専用UID。
   UIDの仮値は登録しない。アプリ利用者は管理者設定を作成・変更できない。
4. エミュレーター検証済みの `production-admin-readonly-stage1.rules` を適用する。現在のplayers規則を保持し、専用UID＋passwordプロバイダ＋失効時刻の検証を満たす管理者にだけ管理情報の読み取りを追加。管理コレクションの作成・更新・削除は、管理者にも許可しない。
5. Webコードを読み取り専用版へ更新し、`enabled=true`、`adminReadOnly=true`、`managementEnabled=false`、`seasonManagementEnabled=false` とする。完全な設定案は `environments/production-admin-stage1.proposed.json`。児童同期・旧ランキングのフラグは維持する。管理室APIと画面の両方に書き込み停止を追加。パスワード変更ボタンも出さない。この段階のログアウトは当該端末の認証解除のみで、全端末失効は行わない。

Rules差分は `firebase/production-admin-readonly-stage1.diff`。公開中のプレイヤー文書への変更権限は増えず、削除禁止・分配①記録の減少禁止も維持する。設定案とWebコードは未反映のブランチに置き、承認前に本番へ適用しない。

### 重要な適用範囲

第1段階では、既存の児童向けランキングを壊さないため、現行の「認証済み利用者がplayersを読める」規則を保持する。**全児童データを管理者以外から非公開にする要件は、この段階では未達成**。管理者情報・操作履歴・バックアップは管理者専用にできるが、playersの閲覧制限には、公開ランキング用の情報を別コレクションへ分離し、児童側の読み取りを切り替える作業が必要。これをせずplayersの一覧読み取りを管理者限定にすると、現在のランキング表示が止まる。

この互換性例外を明示した第1段階だけが今回の承認範囲であり、将来の公開ランキング分離や管理書き込み権限まで承認したことにはしない。

## 検証結果と限界

再実行コマンド：`npm run test:admin-stage1`。実Firebaseには接続しない。

- 本番Consoleで認証方式、専用アカウント検索、管理者設定の不存在、最新公開Rulesを読み取り確認。
- 総まとめの保留画面を本番で確認。既存ゲームと保存データは削除していない。
- 新しいRulesはローカルFirestore/Auth Emulatorで15件成功。パスワード正誤、専用管理者のsnapshot取得、未認証・匿名・別UID・同UID Google・失効トークンの拒否、権限自己付与の拒否、管理書き込みの拒否、他児童のポイント・名前・記録・所持品の変更拒否、分配記録保持、ログアウトを検証した。
- 本番の管理者ログインや書き込みは未検証。アカウント・初期設定・Rulesが未作成なので、成功したとは報告しない。
- 第1段階の案で、既存のplayers一覧読み取りを保持することも明示的にテストした。この制約は全機能完成時に解消する必要がある。

I've set up prototype Security Rules to keep the data in Firestore safe. They are designed to be secure for limiting management reads to the provisioned password administrator and denying all management writes in this first stage. However, you should review and verify them before broadly sharing your app. If you'd like, I can help you harden these rules.

## 影響範囲と復旧方法

- 第1段階で増えるのはAuth専用1アカウント、private配下2文書、管理者向け読み取り権限。players・ポイント・称号・ランキング・購入・所持品の移行、書換、初期化は行わない。料金プランも変更しない。
- 問題があれば最初に本番Webを `enabled=false` へ戻して管理入口を停止。
- 保存した現行RulesをConsoleへ戻す。これで管理専用パスへのアプリからのアクセスは拒否される。古いリポジトリのRulesへは戻さない。
- 新設した管理者をAuthで無効化し、管理者ACLのenabledをfalseにする。復旧で既存の児童アカウントを触らない。
- private初期文書は復旧のため保持する。メール/パスワード認証自体をOFFへ戻すのは、その時点で専用以外の利用者がいないことを再確認し、承認後に行う。
- 第1段階は児童データの変更をしないため、児童データをバックアップから書き戻す復旧操作は不要。
