# プレイヤー情報同期 第2弾：設計・実装・検証記録

2026年10月27日。確認用サイト限定。実Firebase稼働は追加設定待ち。

## 現状調査とデータの対応

本番はFirebase project `manabi-game-land` のplayersと、接頭辞なしの端末記録を使う。今回これらは読まず・変更せず、移行もしない。

確認用は `manabi_public_preview:` の端末保存を使い、管理室だけが別プロジェクト `manabi-game-landcheck` の `previewSpark/v1` に接続していた。確認用ゲームの一般プレイヤーを識別するAuth UIDはまだなかった。

| 情報 | 確認用の端末保存 | 確認用Firestore |
|---|---|---|
| プレイヤーID | Firebase匿名認証の永続セッション＋mgl_sync_v2.uid | players/{Auth UID} の文書ID・uid |
| 名前 | mgl_nickname | nickname（登録後は管理室が変更） |
| 所持ポイント・購入品 | mgl_economy_v1 | balances、owned |
| 算数の最高記録 | mgl_best | best.keisan |
| その他の最高記録 | mgl_{ゲームID}、都道府県の旧mq_pref_name/place | best.{ゲームID} |
| 獲得称号 | 最高記録からの既存判定＋mgl_sync_titles_v2 | titles（和集合） |
| 装備 | mgl_profile | appearance、appearanceRevision |
| 利用状態 | 同期時に参照。ローカルで権限変更しない | status（児童から変更不可） |

ゲーム別bestは計算のきまり・都道府県の名前・場所・アルファベット・ことわざ・分配法則の6ゲーム。管理室は従来のplayersを読むので別の管理一覧DBは作らない。管理室の一覧へ所持品・装備の詳細列を追加した。

教科別ポイントは既存のmgl_economy_v1を表示・プレイ用の端末キャッシュとして使い、同期開始後の共有残高と購入確定はFirestoreのbalancesを正本とする。旧mgl_pointsなどは削除せず、もう一度残高へ合算することもしない。

初期無料4アイコンは共通カタログで常時所有する扱い。クラウドownedは購入済み・限定報酬・既存所持情報を保存する。

## IDと移行方針

- ニックネームでアカウントを検索・統合しない。同名でも別UIDなら別プレイヤー。
- 最初の有効化時、確認用の元保存をmgl_sync_original_v2へ一度保存し、その後も消さない。
- クラウドにまだ自分のUID文書がない場合だけ、その端末の残高・所持品を初回移行する。
- 同じUIDに既存クラウド残高があり、新しい端末にも正の旧残高があるなど、重複か未移行か判断できない場合は自動合算しない。migration-review-requiredとして、端末データを保持して止める。
- Firebaseの現在UIDと、保存済みの対応UIDが異なった場合も自動で移し替えない。
- 匿名認証はブラウザー単位。同じ児童が別端末でも同じUIDを使うためのアカウント連携・引き継ぎ画面は今回追加していない。別端末へ勝手に同名アカウントを結び付けない。同一UIDの並行クライアント競合はEmulatorで検証した。
- 端末内ランキングの自分の行は、名前ではなく固定localPlayerIdで更新し、管理室での名前変更時の二重行を防ぐ。古い他の行は保持する。

## 同期・競合の処理

- 保存変更を約1.8秒まとめて送信し、再接続・画面再表示でも再試行する。定期的な全プレイヤー読込はしない。
- bestは各ゲームの大きい値、称号・所持報酬は和集合で保持する。
- 自分のplayers文書だけを変更通知で読み、管理室の名前・利用状態を端末へ反映する。
- 児童の通常同期ではnickname、status、管理者監査フィールドを書き込まない。古い端末名で管理室の変更を戻さない。
- 装備にはappearanceRevisionを使う。別端末が先に変更していた場合は新しいクラウド装備を優先し、競合した端末の装備を別の端末保存へ退避する。報酬の自動装備はしない。
- 同時取引の競合でRules拒否が返った場合は、実際にrevisionが先へ進んでいたことを再読込で確認した場合だけ、最大3回再試行する。一般的な権限拒否を無条件に再試行しない。

## ポイントと購入

残高のmax比較だけでは、購入前の古い端末が減算を取り消してしまうため採用していない。

- devices/{端末ID}に教科別の単調増加する加算カウンターを置く。
- Firestore取引で、前回確認済みカウンターとの差分だけを残高へ追加する。
- 同じカウンターを再送しても二重加算しない。購入減算はカウンターを戻さない。
- 購入はオンライン時だけ、players残高・所有情報・purchases/{商品ID}の購入証跡を同じ取引で確定する。
- Rulesはカタログの価格・選択教科・残高不足・重複所有・限定商品の購入禁止を検査する。購入後に自動装備しない。
- 通信障害中の学習記録・未送信加算は端末に保持する。通信完了前の新規購入ではポイントを減らさない。
- 有効化前は既存のローカル購入処理を維持する。有効化後は複数端末での二重減算を防ぐため、新規購入にはオンライン接続が必要になる。

## Rulesで保証する範囲と限界

一般プレイヤーは署名済み匿名Auth UIDと一致する自分のplayers文書だけを取得・同期できる。一般プレイヤーの全員一覧取得、他UIDの読書き、管理者権限の変更、status・nicknameの変更、監査履歴・バックアップの改変を拒否する。

通常同期のポイントは「カウンター差分と残高変更が一致」「カウンターを後退させない」を検査し、購入は「価格分だけ減算」「所有と購入証跡が同時に増える」を検査する。最高記録の低下、称号・所有の削除を拒否する。管理室の名前変更・バックアップ・履歴の原子的保存は第1弾Rulesを維持している。

**正誤・初回移行元の残高・最高記録・加算カウンターの増加量はクライアント申告のため、正しい学習から生じた値であることは証明できない。** 自分のUIDで初期残高を偽る、加算カウンターや最高記録を作為的に増やす、自動回答する等の不正を完全には防げない。初期所有の真正性もサーバー採点・独立した移行証跡なしでは保証できない。1日50ptの正解付与制限も既存のクライアント処理が基本で、複数端末や改造クライアントを含む厳密なサーバー全体上限は未実装。

新しい最高称号報酬の所持追加は保存済みbestの条件に合わせて検査するが、そのbest自体の正しさをサーバーが採点するわけではない。全ゲームのサーバー採点への置き換えは行っていない。

Firestoreのplayersにはポイント等の個人情報があるため、一般児童へ他プレイヤーの文書は公開しない。共有ランキングの公開用投影は今回追加していない。既存の確認用ランキング表示は端末内のまま。adminTestの記録は同期・通常ランキング登録ともに除外する。

## 検証

Firebase Auth/Firestore Emulatorのdemoプロジェクトで **43件すべて成功**。本番データを使っていない。

- 第1弾の管理認証、一覧、名前変更、履歴・バックアップ、ログアウト後の古いトークン拒否を再検証。
- 初回移行、700問の保持、二重加算防止、購入済みポイントの復活防止、同一UIDの同時更新・最高値の統合、二重購入防止、残高不足拒否、限定商品の購入禁止、最高称号報酬の後付け、装備競合、管理室の変更名の保持を検証。
- 他人の文書、一覧取得、管理権限、直接残高変更、購入証跡の改変、加算カウンターの巻き戻しを拒否するテスト。
- 通信待ちの未確認加算を端末残高へ含める計算、再送時の冪等性、停止中プレイヤー、曖昧な二重移行の停止、同名別UID、テスト専用コレクション隔離を検証。
- 同期機能が無効の間の従来ショップ購入と、adminTest時の購入除外を検証。

実Firebaseでは匿名Authのテストを1回実行し、HTTP400 ADMIN_ONLY_OPERATIONで失敗した。新しいAuthユーザー・プレイヤー文書は作られていない。実Firebaseでの第2弾同期・管理室との双方向表示・通信切断復帰・実機の並行操作は未検証。
